Design Document

Generalized Phenotype Composition

Design plan for phenotype_components, composite traits, RR, and heterogeneous residuals

Plan: Generalized Phenotype Composition

Motivation

Some traits recorded on individuals are not a direct function of that individual’s own genotype alone. Three key classes:

  • Maternal traits (e.g. weaning weight in beef cattle): the calf’s phenotype is a function of the calf’s own direct genetic effect and the dam’s maternal genetic effect (MILK). Both contribute to the same observed record.
  • Social / competition traits (e.g. competition in livestock pens, neighbor effects in forestry): an individual’s phenotype depends on its own genetic effect plus the summed (or averaged) genetic effects of others sharing its environment (pen, plot, cage, spatial neighborhood).
  • Random regression / reaction norm traits (e.g. test-day milk yield, growth curves, reaction to temperature): the phenotype at covariate value t is a linear combination of multiple genetic component TBVs (intercept, slope, higher-order terms) each weighted by a basis function of t (raw polynomial or Legendre polynomial).

The current add_phenotype() assumes a single trait with a single TBV sourced from the focal individual. This plan describes a generalized composition system that decouples genetic component traits (things with QTL effects and TBVs) from observed phenotypic traits (things recorded in ind_phenotype, assembled from one or more component TBVs potentially sourced from different individuals and weighted by potentially dynamic functions of a covariate).

Refactor Summary: What Changes

Authoritative checklist of every table and function touched by this refactor. Read this before the detailed sections below. Items marked [deferred] are explicitly out of scope for the first implementation pass.

New Tables

All three tables are created eagerly and empty by initialize_genome(), exactly like ind_meta, ind_phenotype, and the other core tables. This means mutate_table() can be called on any of them immediately after initialization, before any define_* call, allowing users to pre-declare typed custom columns.

Table Rows written by Purpose
phenotype_meta define_phenotype() One row per observed phenotype. Stores all phenotype-level metadata: trait_type, repeatable, expressed_sex, mean (phenotypic intercept), min_value, max_value, prevalence, thresholds. Does not store index_weight or economic_value — those belong exclusively in index_meta where per-index per-trait weights are defined. Replaces the phenotype columns currently in trait_meta.
phenotype_components define_phenotype(components =) One row per (phenotype × component trait × contributor × weight rule). Defines how add_phenotype() assembles a composite genetic value from one or more trait_name TBVs. Empty for simple single-self traits.
phenotype_residual_cov define_effect_cov_matrix(pop, "residual", R), define_phenotype(residual_var =), add_residual_cov() Residual (co)variances keyed by phenotype_name_1 / phenotype_name_2. Supports unconditional defaults (condition_column = NULL) and group-heterogeneous residuals (condition_column, condition_level). Includes weight_type and poly_order columns for future RR covariate-continuous residuals (schema reserved now; lookup logic deferred).

define_effect_cov_matrix() — routing change based on effect_name:

Repeatability model recipe (scenario 2):

pop <- pop |>
  define_trait("litter_size", ..., repeatable = TRUE, residual_var = 0.5) |>
  define_effect_random("litter_size", "pe",
    source_column = "id_ind",    # one PE draw per animal
    variance = 0.3)

Each successive call to add_phenotype("litter_size") for the same sow reuses her stored PE draw and adds an independent residual, reproducing the classical repeatability model y_ij = mu + TBV_i + PE_i + e_ij.

Naming Convention

Two distinct namespaces are used throughout this plan and must not be conflated:

  • trait_name — a genetic component trait. Has QTL effects in genome_effects, a TBV in ind_tbv, and a (co)variance in trait_effect_cov. Examples: WWD, WWM, RR_intercept, RR_slope_age, L0_milk, SGE. Always registered in trait_meta.

  • phenotype_name — the observed phenotype written to ind_phenotype. For simple (non-composite) traits, phenotype_name == trait_name. For composite traits the names differ: phenotype_name = "WW" is assembled from trait_name = "WWD" and trait_name = "WWM". The phenotype_components table provides the assembly rules.

The add_phenotype() argument refers to phenotype_name. The TBVs it pulls internally are identified by trait_name via phenotype_components. When no rows exist in phenotype_components for a given phenotype_name, the fallback assumes phenotype_name == trait_name (current single-trait behavior is preserved).

Core Concept

WWD (weaning weight direct) and WWM (weaning weight maternal) are defined as regular traits in tidybreed — they have QTL effects in genome_effects, variances in trait_effect_cov, and TBVs in ind_tbv. Nothing special about them.

WW (the observed weaning weight phenotype) is defined by a composition rule stored in a new table phenotype_components:

pheno(WW, calf_i) = TBV(WWD, self) + TBV(WWM, dam_of_i) + residual(WW)

For social / competition traits:

pheno(Competition, individual_i) = TBV(CompetitionDirect, self)
                                 + sum(TBV(SGE, penmate_j) for j in pen_of_i)
                                 + residual(Competition)

For a linear random regression on age:

pheno(milk, i, age) = TBV(RR_intercept, i) * 1.0
                    + TBV(RR_slope,     i) * age
                    + residual(milk)

For a Legendre polynomial random regression on days-in-milk (DIM):

pheno(milk, i, dim) = TBV(L0_milk, i) * phi_0(dim)
                    + TBV(L1_milk, i) * phi_1(dim)
                    + TBV(L2_milk, i) * phi_2(dim)
                    + residual(milk, dim)

where phi_k(dim) is the k-th Legendre polynomial evaluated at dim, scaled to [-1, 1] over [dim_min, dim_max].

add_phenotype("WW") checks phenotype_components for rows where phenotype_name = "WW". If none exist, it falls back to current single-trait behavior. If rows exist, it resolves each contributor, fetches TBVs, computes weights (fixed or dynamic), aggregates, and adds a residual drawn from trait_effect_cov for phenotype_name = "WW".

Proposed New Table: phenotype_components

One row per (observed phenotype × component trait × contributor × weight rule).

Core columns (all cases)

Column Type Notes
id_phenotype_comp INTEGER Primary key (auto-incrementing)
phenotype_name VARCHAR The observed phenotype name written to ind_phenotype
source_trait_name VARCHAR FK to trait_meta.trait_name - which component TBV to pull
contributor_type VARCHAR "self", "dam", "sire", "group"
group_column VARCHAR NULL unless contributor_type = "group"; column defining group membership (e.g. "pen_id")
group_table VARCHAR Table containing group_column; default "ind_meta"
aggregation VARCHAR "sum" or "mean"; relevant when contributor_type = "group"

Weight columns

Column Type Notes
weight DOUBLE Scalar multiplier applied after the dynamic weight; default 1.0
weight_type VARCHAR "fixed", "covariate", "legendre", or "raw_poly"; see descriptions below
covariate_name VARCHAR Covariate key; column in covariate_table or a key in covariate_values
covariate_table VARCHAR Table to read from (default "ind_meta"); NULL = value supplied at call time
poly_order INTEGER Basis order (0=intercept, 1=slope, 2=quadratic); NULL when weight_type = "fixed"
poly_scale_min DOUBLE Covariate value mapping to -1 for Legendre scaling; NULL = use observed minimum
poly_scale_max DOUBLE Covariate value mapping to +1 for Legendre scaling; NULL = use observed maximum

weight_type values:

  • "fixed": effective weight = weight scalar (current default behavior)
  • "covariate": effective weight = covariate_value * weight
  • "legendre": effective weight = phi_{poly_order}(scale(covariate_value)) * weight
  • "raw_poly": effective weight = covariate_value ^ poly_order * weight

Genome effect type column

Column Type Notes
genome_effect_types VARCHAR Effect types to include; default "additive"

Comma-separated. Valid values now: "additive". Future: "additive,dominance", "additive,dominance,epistasis". Controls which rows in genome_effects are summed when computing the TBV for this component.

How the Key Examples Map

Weaning weight (maternal trait)

phenotype_name source_trait_name contributor_type weight_type weight genome_effect_types
WW WWD self fixed 1.0 additive
WW WWM dam fixed 1.0 additive

WWD and WWM are defined independently with their own QTL effects and variances. WW only needs a residual variance in trait_effect_cov and a trait_type in trait_meta. No genome_effects rows needed for WW itself.

Social / competition trait (group-based aggregation)

phenotype_name source_trait_name contributor_type group_column aggregation weight_type weight genome_effect_types
Competition CompetitionDirect self NULL sum fixed 1.0 additive
Competition SGE group pen_id sum fixed 1.0 additive

The pen_id column must exist in ind_meta (or the specified group_table). At phenotype time, add_phenotype() finds all individuals sharing the same pen_id as the focal individual and sums their SGE TBVs.

Linear random regression on age

phenotype_name source_trait_name contributor_type weight_type covariate_name covariate_table poly_order genome_effect_types
milk_at_age RR_intercept self fixed NULL NULL NULL additive
milk_at_age RR_slope self covariate age NULL (call-time) NULL additive

covariate_table = NULL signals that the covariate value is supplied at add_phenotype() call time (e.g. add_phenotype("milk_at_age", covariate_values = list(age = 365))). The value is written into ind_phenotype as a user column so the record is self-describing. Alternatively, covariate_table = "ind_meta" reads age from ind_meta at computation time — suitable when each individual has a single fixed covariate value.

Legendre polynomial RR on days-in-milk (DIM)

phenotype_name source_trait_name contributor_type weight_type covariate_name poly_order poly_scale_min poly_scale_max genome_effect_types
milk L0_milk self legendre dim 0 5 305 additive
milk L1_milk self legendre dim 1 5 305 additive
milk L2_milk self legendre dim 2 5 305 additive

Called once per DIM point:

for (day in c(50, 100, 150, 200, 250, 305)) {
  pop <- pop |>
    get_table("ind_meta") |>
    filter(sex == "F") |>
    add_phenotype("milk", covariate_values = list(dim = day))
}

Each call writes one record per cow to ind_phenotype with trait_name = "milk" and dim = day stored as a user column.

Proposed Function API: define_trait() and define_phenotype()

These two functions own completely separate concerns and must not overlap.

define_trait() — Genetic Component Traits (Revised)

Registers a QTL component trait: a genetic quantity with effects in genome_effects, TBVs in ind_tbv, and additive genetic variance in trait_effect_cov. Contains no phenotype-level information whatsoever.

Writes one row to trait_meta (genetic columns only).

Arguments:

Argument Type Notes
trait_name VARCHAR Unique identifier for this genetic component trait
target_add_var DOUBLE Target additive genetic variance; written to trait_effect_cov[gen_add]
target_add_mean DOUBLE TBV centering mean; default 0
expressed_parent VARCHAR Imprinting: "both" (default), "parent_1", "parent_2"
description VARCHAR Optional free text
units VARCHAR Optional (e.g. "kg")
overwrite LOGICAL Replace an existing row; default FALSE

Removed from define_trait() — these move to define_phenotype(): trait_type, repeatable, expressed_sex, mean, min_value, max_value, prevalence, thresholds, residual_var. index_weight and economic_value are removed entirely — they belong only in index_meta where per-index per-trait weights are defined. Use define_index(). recorded_on is deprecated — superseded by the components argument in define_phenotype().

define_phenotype() — Observed Phenotypes (New)

Registers an observed phenotype: the quantity written to ind_phenotype and drawn by add_phenotype(). For simple traits phenotype_name == trait_name and define_trait() must already exist for that name. For composite traits no define_trait() call is needed for the composite name — define_phenotype() creates its own row in phenotype_meta (or trait_meta; see open question Q7).

Writes to phenotype_meta and, if components is supplied, to phenotype_components. If residual_var is supplied, writes one unconditional row to phenotype_residual_cov (condition_column = NULL). For heterogeneous residuals, call add_residual_cov() afterwards.

Arguments:

Argument Type Notes
phenotype_name VARCHAR Name of the observed phenotype; equals trait_name for simple traits
trait_type VARCHAR "continuous", "count", "binary", "categorical"
mean DOUBLE Phenotypic intercept (population mean); stored as target_add_mean; default 0
expressed_sex VARCHAR Who receives a record: "both" (default), "M", "F"
repeatable BOOLEAN Multiple records per individual allowed; default FALSE
min_value DOUBLE Lower clip bound for count traits
max_value DOUBLE Upper clip bound for count traits
prevalence DOUBLE Threshold prevalence for binary traits
thresholds VARCHAR Comma-separated cutpoints for categorical traits
residual_var DOUBLE Scalar residual variance; writes to phenotype_residual_cov, condition_column = NULL
components data.frame One row per component; maps to phenotype_components. NULL = simple single-self.
overwrite LOGICAL Replace existing rows; default FALSE

components column spec — unspecified columns get the listed defaults:

Column Required Default
source_trait_name Yes —
contributor_type Yes —
weight No 1.0
weight_type No "fixed"
covariate_name No NULL
covariate_table No NULL
poly_order No NULL
poly_scale_min No NULL

Complete Worked Examples

  define_trait("ADG",
    target_add_var = 100,
    units          = "g/day") |>
  get_table("genome_meta") |>
  filter(chr %in% 1:5) |>
  define_additive_effects("ADG") |>
  define_phenotype("ADG",
    trait_type   = "continuous",
    mean         = 500,
    residual_var = 120) |>
  define_effect_fixed_class("ADG", "sex",
    source_column = "sex",
    levels        = c(M = 20, F = 0))

2 — Repeatability model (litter size, scenario 2):

pop <- pop |>
  define_trait("litter_size", target_add_var = 0.3) |>
  get_table("genome_meta") |>
  define_additive_effects("litter_size") |>
  define_phenotype("litter_size",
    trait_type   = "count",

define_trait_simple() — Updated Convenience Wrapper

define_trait_simple() is updated to chain all three setup steps for simple non-composite traits:

define_trait_simple(pop, trait_name, n_qtl,
                    target_add_var,
                    mean          = 0,
                    residual_var,
                    trait_type    = "continuous",
                    expressed_sex = "both",
                    repeatable    = FALSE, ...)

Internally: define_trait() → sample n_qtl random loci → define_additive_effects() → define_phenotype().

How add_phenotype() Would Use This

  1. Query phenotype_components for rows matching phenotype_name.
  2. If no rows → current behavior (single-trait, self, weight_type = "fixed", genome_effect_types = "additive").
  3. If rows exist:
    1. Resolve covariate value(s) needed for dynamic weights: check covariate_table (look up from DB) or covariate_values argument (supplied at call time).
    2. For each component row, resolve the contributing individual(s):
      • "self" → focal individual
      • "dam" → ind_meta.id_parent_2 of focal individual
      • "sire" → ind_meta.id_parent_1 of focal individual
      • "group" → all individuals where {group_table}.{group_column} matches focal individual’s value
    3. Fetch TBVs for source_trait_name from ind_tbv for the resolved set, filtered to the genome_effect_types specified in that row.
    4. Aggregate (sum or mean) across group members when contributor_type = "group".
    5. Compute the effective weight for this component:
      • "fixed": use weight scalar directly
      • "covariate": weight = covariate_value * weight
      • "legendre": weight = phi_{poly_order}(scale(covariate_value)) * weight
      • "raw_poly": weight = covariate_value^poly_order * weight
    6. Multiply aggregated TBV by effective weight.
    7. Sum all components to get the composite genetic value.
  4. Add fixed/random covariate contributions (same as current logic, sourced from trait_effects for phenotype_name).
  5. Draw residual from trait_effect_cov under effect_name = "residual" for phenotype_name. (For RR traits with heterogeneous residual variance, see open question 8.)
  6. Write record to ind_phenotype under phenotype_name. If covariate_values were supplied, write them as additional user columns on the record.

Relationship to Existing Tables

  • trait_meta: All trait_names (component traits WWD, WWM, L0_milk, …) AND all phenotype_names (WW, milk) live here. Composite phenotypes need a trait_type and a residual variance but have no genome_effects rows. Consider adding is_composite BOOLEAN to make this explicit; alternatively, the presence of rows in phenotype_components is a sufficient implicit signal.
  • trait_effect_cov: Home for genetic additive (G) and named random-effect covariances, all keyed by trait_name_1/trait_name_2. Residual (R) covariances move to the new phenotype_residual_cov table so that trait_name and phenotype_name namespaces remain strictly distinct (see Residual Variance section).
  • genome_effects: No changes required. Each component trait_name has its own rows with the appropriate genome_effect_type ("additive" now; "dominance" and "epistasis" later). The genome_effect_types column in phenotype_components controls which rows are summed when computing the TBV for that component.
  • ind_tbv: Component trait TBVs (WWD, WWM, L0_milk, etc.) are stored here as usual, keyed by trait_name. Storing the composite genetic value (e.g. WW_TBV(self) = WWD_TBV + WWM_TBV) under phenotype_name is an open question (see Q2). Currently ind_tbv holds strictly additive TBVs; a future genome_effect_types expansion may require distinguishing rows by effect type.
  • recorded_on in trait_meta: Deprecated. phenotype_components (populated by define_phenotype(components = ...)) is a strict superset. The column will be removed in a future schema migration.

Residual Variance: Naming and Heterogeneity

The Naming Problem

In the current implementation, trait_effect_cov stores residual entries as (effect_name = "residual", trait_name_1 = "WWD", trait_name_2 = "WWD"). This is semantically wrong once composite phenotypes are introduced: WWD is a genetic component trait that is never directly observed and has no residual of its own. Only WW (the observed phenotype) has a residual. Residuals belong to the phenotype namespace (phenotype_name), not the genetic component namespace (trait_name).

The same applies to simple non-composite traits. A trait such as ADG can have a residual variance that differs by farm, sex, or contemporary group — none of which has anything to do with the trait’s QTL structure. Separating residual storage into its own table with phenotype_name keys makes this distinction explicit.

Design Options

Option A — New phenotype_residual_cov table (Recommended)

Keep trait_effect_cov unchanged for genetic additive (G) and named random-effect covariances, all keyed by trait_name_1/trait_name_2. Add a separate table for residual (R) covariances keyed by phenotype_name_1/phenotype_name_2, with optional conditioning columns for heterogeneous variance by group.

Option B — Rename columns in trait_effect_cov

Rename trait_name_1/trait_name_2 to neutral name_1/name_2 and add conditioning columns directly. Convention: gen_add rows use trait_name values; residual rows use phenotype_name values. Fewer tables, but semantically mixed and the convention is implicit rather than enforced by schema.

Proposed New Table: phenotype_residual_cov

Column Type Notes
id_residual_cov INTEGER Primary key (auto-incrementing)
phenotype_name_1 VARCHAR FK to trait_meta (phenotype namespace)
phenotype_name_2 VARCHAR FK to trait_meta (phenotype namespace)
cov_value DOUBLE Variance (diagonal) or covariance (off-diagonal)
condition_column VARCHAR Column in condition_table defining the group; NULL = unconditional default
condition_table VARCHAR Table containing condition_column; default "ind_meta"
condition_level VARCHAR Specific group level/value this row applies to; NULL = default fallback

Both (i, j) and (j, i) directions are stored for off-diagonal entries, matching the trait_effect_cov convention.

Lookup Hierarchy in add_phenotype()

For each individual at phenotype time:

  1. Determine the individual’s value of condition_column from condition_table.
  2. Look for a row matching (phenotype_name, condition_column, condition_level).
  3. Fall back to the unconditional row (condition_column = NULL) if no exact match.
  4. Warn and use the unconditional default row if neither a group-specific nor an unconditional row is found (see Design Decision 9).

Examples

Farm-heterogeneous residual variance for WW:

phenotype_name_1 phenotype_name_2 cov_value condition_column condition_level
WW WW 120.0 NULL NULL
WW WW 95.0 farm_id Farm_A
WW WW 145.0 farm_id Farm_B

Individuals on Farm_A use Var(e) = 95; Farm_B use 145; any other farm falls back to 120.

Sex-specific residual variance for ADG:

phenotype_name_1 phenotype_name_2 cov_value condition_column condition_level
ADG ADG 80.0 NULL NULL
ADG ADG 70.0 sex M
ADG ADG 90.0 sex F

Correlated residuals with heterogeneous variance (two traits):

All four entries — (WW, WW), (WW, BW), (BW, WW), (BW, BW) — are stored per condition group. add_phenotype() assembles the sub-matrix R for the individuals sharing a condition group and draws jointly from MVN(0, R).

API

Three entry points write to phenotype_residual_cov, in order of typical use:

1. define_effect_cov_matrix(pop, "residual", R) — primary multi-trait path. When effect_name = "residual", the function routes to phenotype_residual_cov instead of trait_effect_cov. Matrix row/column names are treated as phenotype_name_1 / phenotype_name_2. Both (i, j) and (j, i) directions are stored. condition_column = NULL and condition_level = NULL (unconditional default row). This is the recommended path when two or more phenotypes share correlated residuals, and can be called before define_trait() or define_phenotype().

R <- matrix(c(120, 30, 30, 80), 2, 2,
            dimnames = list(c("WW", "BW"), c("WW", "BW")))
pop <- pop |> define_effect_cov_matrix("residual", R)

2. define_phenotype(pop, phenotype_name, residual_var = ...) — single-trait shorthand. Writes one diagonal entry to phenotype_residual_cov for this phenotype (condition_column = NULL, condition_level = NULL). Off-diagonal covariances between this phenotype and others are not touched; they default to 0 unless define_effect_cov_matrix() has already set them. Use this shorthand when phenotypes are modelled independently (no joint residual draw needed).

3. add_residual_cov(pop, phenotype_names, cov_matrix, condition_column = NULL, condition_table = "ind_meta", condition_level = NULL) — conditional / heterogeneous residuals. Adds group-specific rows after define_phenotype() or define_effect_cov_matrix() has written the unconditional default. Each call writes one condition group’s covariance matrix.

pop <- pop |>
  add_residual_cov("BW_turkey",
    cov_matrix       = matrix(900, 1, 1, dimnames = list("BW_turkey", "BW_turkey")),
    condition_column = "sex",
    condition_level  = "M") |>
  add_residual_cov("BW_turkey",
    cov_matrix       = matrix(400, 1, 1, dimnames = list("BW_turkey", "BW_turkey")),
    condition_column = "sex",
    condition_level  = "F")

Implementation Gaps and Refactoring Notes

These are specific code paths that must change when phenotype_components and phenotype_residual_cov are introduced. Documented here to prevent surprises during the refactor.

G1 — add_phenotype() genome_effects validation must become conditional

add_phenotype.R:158-175 errors if a trait has zero additive effect rows in genome_effects. For composite phenotypes (e.g. WW) this will always fire: WW has no own QTL — its genetics come from WWD and WWM.

Fix: before the validation loop, check whether phenotype_components has any rows for phenotype_name = t. If yes, skip the additive-effects guard entirely. The component traits (WWD, WWM) will be validated when their TBVs are fetched.

G2 — add_tbv() inside add_phenotype() must use component trait names

add_phenotype.R:217: pop <- add_tbv(tbl, trait_name = trait) is called with the observed phenotype name. For composites, add_tbv() must be called for the component source_trait_name values ("WWD", "WWM"), not "WW". The refactored code should query phenotype_components for all distinct source_trait_name values across the requested phenotypes, union them, and call add_tbv() once for that combined set. Component traits have target_add_mean = 0 (TBVs are Falconer-centered at base allele frequencies); the composite phenotype WW carries its own target_add_mean (population mean of the observed phenotype) in trait_meta — no change to that lookup is needed.

G3 — Residual lookup must shift from trait_effect_cov to phenotype_residual_cov

add_phenotype.R:396: resid_var <- get_effect_var(pop, "residual", t) queries trait_effect_cov using trait_name. After the plan is implemented:

  1. For the unconditional case (no heterogeneity), phenotype_residual_cov with condition_column = NULL replaces the existing trait_effect_cov lookup.
  2. For the conditional case, a new helper (e.g. get_residual_cov(pop, phenotype_name, ind_row)) queries phenotype_residual_cov for the individual’s group value, falls back to the unconditional row, warns and counts individuals using the fallback.

The existing get_effect_var() / load_effect_cov() functions remain unchanged for genetic and named random-effect covariances.

G4 — NULL in source column behaves differently for fixed_class vs random effects

In compute_covariate_contribution() (phenotype_helpers.R):

  • fixed_class: NULL source value → as.character(NA) = "NA" → not in levels_json → hard error. Correct strict behaviour for fixed effects where every individual must have a known level.
  • random: NULL source value → existing_map["NA"] → NA → silently replaced by 0 (line 252). The individual contributes nothing for this effect with no warning.

These asymmetries should be documented in function roxygen; see Q15 for resolution.

G5 — Multi-phenotype joint residual draw must handle phenotype_residual_cov and heterogeneous groups

The joint residual sampling block (add_phenotype.R:354-372) calls load_effect_cov(pop, "residual", trait) where trait is the vector of requested phenotype names. After the plan, residuals live in phenotype_residual_cov.

The refactored block must:

  1. Query phenotype_residual_cov for the requested phenotypes.
  2. Split individuals by condition group (e.g. all Farm_A individuals share one R matrix, Farm_B individuals share another).
  3. For each condition-group batch, assemble the appropriate R sub-matrix and draw from MVN(0, R_group) for that batch.
  4. Combine batch draws back into a single matrix ordered by id_ind.

If individuals fall back to the unconditional row (mixed-group scenario), warn and count them. This is a meaningfully more complex joint-draw than the current single-pass MASS::mvrnorm() call.

G6 — Higher-order polynomial fixed covariates are not natively supported

define_effect_fixed_cov() stores one slope × (x − center) term. There is no poly_order column in trait_effects. To fit a quadratic on age today a user must:

  1. Pre-compute age_sq as a column in ind_meta via mutate_table().
  2. Call define_effect_fixed_cov() twice: once on age and once on age_sq.

This is a workable workaround but requires the user to manage derived columns. See Q14 for a proposed schema extension.

Design Decisions

The questions below were reviewed and resolved. Each entry states the decision and the rationale so implementers do not need to re-open them.

  1. Composite genetic value in ind_tbv: No. ind_tbv is strictly keyed by trait_name (genetic component trait). No composite row is written under a phenotype_name. The individual component TBVs (WWD, WWM) are stored there; the composite phenotype WW is assembled at phenotype time and written only to ind_phenotype. Storing a composite TBV would be fabricated — it blurs the genetic / phenotypic distinction the decoupled API is designed to preserve.

  2. Missing contributor handling: skip (default) + warning. When a contributor cannot be resolved (no dam record, no pen_id, etc.), add_phenotype() omits that individual from ind_phenotype and emits a warning with a count of affected individuals. A second mode, "error", is available per phenotype_components row via a missing_action VARCHAR column (values: "skip" (default) or "error"). This is the expected behaviour for founders in a maternal-composite scenario — WW for beef cows without dams simply produces no WW phenotype, which is biologically correct. Users who filter add_phenotype() to a broad group (e.g. all of generation 1) and only some individuals qualify (e.g. only on-test animals have a pen_id) will naturally receive phenotypes only for those that qualify, with a warning explaining the rest.

    For standard random effects such as PE — where no draw exists yet for an animal — the contribution defaults to 0 with a warning (existing behaviour preserved).

  3. Spatial / neighborhood contributors: reserved for later. The schema reserves a contributor_filter VARCHAR column in phenotype_components (initialized to NULL, never read in the first refactor). Spatial lookup (adjacent rows/columns, radius-based neighbors) is deferred until a concrete use case is defined. Do not implement in the first refactor.

  4. Ordering of composites in add_phenotype() with no argument: simple sequential. When add_phenotype() is called without a phenotype_name, it first computes and stores TBVs for all traits in trait_meta for the filtered individuals, then assembles all phenotypes registered in phenotype_meta in row order. Since all component TBVs are available before phenotype assembly begins, there are no dependency conflicts and no topological sort is needed.

    Example — beef cattle with WWD, WWM, IMF as component traits and WW + IMF as observed phenotypes: add_phenotype() with no arg computes three TBVs per animal, then produces two phenotypic records per animal (WW and IMF).

  5. Residual heterogeneity for RR traits: implement the schema now. Covariate-continuous heterogeneous residuals (where Var(e) varies smoothly with a value such as DIM or production week) are important for test-day and laying-curve models. The phenotype_residual_cov schema must include weight_type VARCHAR and poly_order INTEGER columns from the first refactor so that a Legendre expansion of residual variance over a covariate can be stored alongside the group-based condition_column / condition_level rows. The lookup logic in add_phenotype() for covariate-continuous residuals may be implemented in a later phase, but the schema must not require migration to accommodate it.

  6. ind_tbv and non-additive effects — plan ind_gv for later. ind_tbv remains strictly for additive breeding values. A future ind_gv table (full genotypic value: A + D or A + D + I) will be added with a dedicated add_gv() function that calls add_tbv() internally. For now, ind_gv is not implemented, but the current schema must not block it. When built, add_gv() will initially produce additive-only genotypic values (identical to TBV until dominance is implemented), giving users the ind_gv table infrastructure without computational overhead for the common additive-only case. Crossbreeding programmes that need dominance deviations will use ind_gv once dominance effects are supported in genome_effects.

  7. phenotype_meta vs trait_meta: new phenotype_meta table. define_phenotype() writes to a separate phenotype_meta table. trait_meta remains purely genetic. add_phenotype() with no arg iterates phenotype_meta only, trivially excluding component-trait rows.

  8. Split tables vs neutral rename for residual covariances: Option A. trait_effect_cov is unchanged (keyed by trait_name_1 / trait_name_2) for genetic additive and named random effect covariances. Residual (co)variances move to a new phenotype_residual_cov table (keyed by phenotype_name_1 / phenotype_name_2) with condition_column, condition_table, condition_level, weight_type, and poly_order columns for heterogeneous and RR residuals. This is semantically clean and avoids mixing genetic and phenotypic namespaces.

  9. Fallback when no matching row in phenotype_residual_cov: warn and use default. When an individual’s group value has no specific row in phenotype_residual_cov, add_phenotype() falls back to the unconditional row (condition_column = NULL) and emits a clear warning stating the phenotype name, condition column, unmatched levels, and the count of affected individuals. No per-phenotype configurability is needed for the initial implementation.

  10. Higher-order polynomial fixed covariates: add poly_order to trait_effects. A poly_order INTEGER column is added to trait_effects (default 1). The contribution of a fixed_cov effect becomes slope × (x − center)^poly_order, so poly_order = 1 preserves the current linear behaviour with no user-visible change. Spline basis functions are not planned.

  11. NULL handling for fixed_class source column: user-controlled via null_class_action. define_effect_fixed_class() gains a null_class_action argument (stored in trait_effects). Available values:

    Value Behaviour
    "skip" (default) Individual is excluded from ind_phenotype for this trait; a warning lists the count and sample id_ind values
    "error" Hard stop when any NULL source value is encountered; use for effects like sex that should never be missing
    "zero" Treat NULL as a zero-shift contribution (equivalent to the reference level); individual receives a phenotype

    The default "skip" is safest: if a user filters a broad group and only some animals have the required column populated, only those animals receive a phenotype, and the warning makes the gap visible without crashing the simulation.
